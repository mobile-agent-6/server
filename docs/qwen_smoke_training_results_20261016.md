# Qwen3-4B 초기·검수본 시험 학습 및 전후 비교 결과

작성일: 2026-10-16 (Asia/Seoul)

실행일: 2026-10-15~16

상태: DATA/AI 내부 시험 학습 결과. 공유 AI 계약·데이터 schema를 확정하지 않는다.

## 결과 요약

Qwen3-4B의 4비트 MLX 모델에 QLoRA 방식으로 20-step 시험 학습을 실행하고, 저장된 어댑터를 다시 불러와 기본 모델과 비교했다. 학습 환경 구축, 학습 입력의 토큰 길이·마스크 검사, 가중치 업데이트, 저장·재로딩 및 검증 입력 비교까지 완료했다. 전체 학습 데이터의 1 epoch 학습이나 배포 모델 완성은 아직 아니다.

초기 미검수 시험은 검증 114행에서 제안 정답 JSON 전체 일치가 23건에서 43건으로 증가했다. 이후 프롬프트를 v2.5로 정리하고 시범 30개 대화를 로컬 승인본으로 구성해 별도의 20-step 학습을 완료했다. 후속 검증 13행에서는 전체 일치가 5건→5건으로 유지되어 측정 지표의 개선이 확인되지 않았다.

두 시험 모두 **고정된 정답 대화 문맥에서 다음 모델 응답을 생성하는 진단**이다. 실제 일정 처리 성공률이나 기존 Ollama 시스템의 77.5%와 동일한 지표가 아니다. 두 시험은 프롬프트·데이터·분모가 다르므로 서로의 점수를 학습 전후로 연결하지 않는다. 완료 범위는 학습 실행·어댑터 저장·응답 비교·오류 분석이며, 성능 개선과 전체 데이터 학습은 후속 과제다.

## 초기 미검수 시험: 데이터와 실행 기준

- 데이터·실험 런타임 기준 커밋: `39c2d3c518844f09e31545ea1df00a37c2489421`.
- 원본: [멀티턴 400개 초안](../datasets/qwen/experiments/multiturn_400_v0.1/README.md).
- train 260개 대화 → 중복 제거된 학습 후보 651행, validation 40개 대화 → 검증 후보 114행.
- test 예약 초안 100개 대화는 이번 학습·모델 비교에 사용하지 않았다. 원본 생성기의 구조·정답 재생 검사와 모델 평가를 구분한다.
- 정답 상태는 모두 `proposed_unreviewed`다. 이번 실행으로 사람이 승인한 데이터로 변경하지 않았다.
- 전달받은 CSV와 기준 커밋의 CSV는 train/validation 내용이 같았다. test의 5개 사용자 발화에서 `오전 8시`와 `아침 8시` 차이가 있었다. 학습·평가의 기준은 JSONL이다.

| 입력 | 행 수 | 최소 토큰 | 최대 토큰 | 평균 토큰(반올림) |
|---|---:|---:|---:|---:|
| train | 651 | 2,428 | 3,244 | 2,699 |
| validation | 114 | 2,419 | 2,915 | 2,625 |

문맥 한도는 3,328토큰으로 설정했다. 검사한 모든 행이 한도 안에 들어갔으며, 마지막 assistant 정답만 학습하도록 prompt mask와 토큰 경계를 검사했다. thinking을 비활성화하는 별도 chat template을 사용했으며 다운로드한 원본 모델은 변경하지 않았다.

학습 콘솔에 표시된 validation loss는 처음 0.377, 10-step 0.132, 20-step 0.266이었다. 적은 검증 배치의 손실이므로 전체 검증 품질이나 최적 체크포인트를 확정하는 근거로 삼지 않는다. 본 보고의 비교는 최종 20-step 어댑터를 사용하며, 10-step 어댑터의 응답 비교는 하지 않았다.

10-step·20-step 체크포인트, 최종 `adapters.safetensors`, `adapter_config.json`의 저장을 확인했다. 모델과 어댑터 파일은 Git에 포함하지 않는다. 이번 설정의 20-step은 20행 분량의 미니배치 연산이며 651행을 전부 한 번씩 학습한 것이 아니다. 같은 batch 설정에서 1 epoch는 대략 651-step에 해당한다.

## 전후 비교 방법

두 실행 모두 같은 MLX 기반 모델, tokenizer, 시스템 프롬프트와 입력 대화 문맥을 사용했다. 차이는 최종 학습 어댑터 적용 여부다. temperature 0, seed 42, 출력 상한 512토큰을 사용했다.

각 행의 마지막 정답 assistant 메시지는 입력에서 제외했다. 이전 정답 대화와 모의 조회 결과 등은 고정 문맥으로 제공했다. 모델이 앞선 턴에서 만든 실수를 다음 턴으로 전파하는 전체 대화 평가는 아니다. 실제 Schedule API, 상태 제어부의 동작, 동적 JSON schema 출력 제약은 적용하지 않았다.

action별 순환 선택 방식으로 10행을 먼저 확인하고, 이후 validation 전체 114행을 별도 실행으로 비교했다. 10행 표본은 입고 관련 사례에 편중되어 대표 성능으로 사용하지 않는다. 전체 비교는 before 114행·after 114행의 ID 순서와 중복 없는 완료를 확인했다. after 실행을 중단·재개했으므로 시간·속도·발열 조건을 통제한 성능 벤치마크로 해석하지 않는다.

## 측정 결과

| 지표 | BEFORE | AFTER | 변화 |
|---|---:|---:|---:|
| 실험 action 검증기 통과 | 62/114 (54.4%) | 76/114 (66.7%) | +12.3%p |
| 검증기 통과 및 action 종류 일치 | 35/114 (30.7%) | 55/114 (48.2%) | +17.5%p |
| 제안 정답 JSON 전체 일치 | 23/114 (20.2%) | 43/114 (37.7%) | +17.5%p |

전체 일치 기준으로 불일치→일치 20건, 일치→불일치 0건, 일치 유지 23건, 불일치 유지 71건이다. 이 기준의 악화 0건을 모든 행동·안전 지표의 악화 0건으로 확대 해석하지 않는다. 형식 통과는 지정된 Python action 검증기의 통과를 뜻하며 모든 프롬프트 규칙이나 사용자 의도 일치를 보장하지 않는다.

| 제안 정답 action | 행 수 | BEFORE 전체 일치 | AFTER 전체 일치 |
|---|---:|---:|---:|
| ANSWER | 15 | 0 | 10 |
| ASK | 34 | 0 | 1 |
| CONFIRM_DELETE | 10 | 4 | 7 |
| CONFIRM_UPDATE | 10 | 0 | 0 |
| CREATE | 10 | 5 | 5 |
| LIST | 35 | 14 | 20 |

`SELECT_TARGET` 정답은 현재 validation에 없어 이번 비교만으로 그 기능의 성능을 판단할 수 없다. `ASK`는 질문의 의미가 같아도 문장이 다르면 전체 불일치다. 1/34를 유효한 질문 성공률로 해석하지 않는다.

주요 개선은 `ANSWER.message=null`, `ASK.request=null`, 삭제 요청의 `targetId` 필드 준수였다. 남은 오류에는 수정 요청의 `targetId` 누락·`operation` 혼용, 날짜·시각이 없는데 등록·조회 시도, 조회의 미완료 조건 누락, 등록과 조회 action 혼동이 있었다. 수정 정답 10행에서는 AFTER 출력 모두 action 검증기를 통과하지 못했다. 이러한 모델 오답만으로 원본 정답이 잘못됐다고 판단하지 않는다.

## 후속 검수본 시험: 준비와 검수 범위

프롬프트 v2.5에서는 등록과 조회의 적용 범위를 분리하고 action별 JSON 예시 8개, 조회 전후 후보 처리, `targetId`와 `operation` 사용을 명시했다. `review_sources.py`의 검수 원본을 현재 제어부로 재생해 실제 모델 호출 시점의 입력·마지막 정답을 만드는 `export_training.py`를 추가했다. 수정된 이전 정답은 후속 턴의 이력에도 반영하며 모델을 호출하지 않는 승인·취소 턴에는 학습 행을 만들지 않는다. 승인된 train/validation만 사용하고 test는 제외한다.

시범 목록의 train 25개·validation 5개 대화를 로컬 `reviewed` 상태로 반영했다. 사용자가 전체적으로 타당하다고 확인하고 기록을 위임한 뒤 Codex가 대화·action·최종 일정 상태를 점검하고 판정을 기록했다. **독립적인 사람 2인 검수나 전체 400건 검수는 아니다.** 30건의 기능 흐름은 성공으로 판정했으며, 4건의 제어부 확인 문구에서 `알림=null`, `완료=true` 등 코드식 표현의 개선 의견을 남겼다. 이 문구는 모델 학습 대상인 action JSON과 구분하며 정답 JSON은 수정하지 않았다. 재생 성공 30/30은 Qwen 모델 성능이 아니다.

| 입력 | 승인 대화 | 모델 호출 | 중복 제거 후 행 | 최소 토큰 | 최대 토큰 | 평균 토큰 |
|---|---:|---:|---:|---:|---:|---:|
| train | 25 | 65 | 63 | 3,367 | 4,169 | 3,648 |
| validation | 5 | 14 | 13 | 3,358 | 3,839 | 3,539 |

문맥 한도 4,352에서 마지막 assistant 마스크 검사와 잘림 없는 입력 준비를 완료했다. 기존 미검수 어댑터를 이어 학습하지 않고 동일한 기본 4비트 모델에서 새 어댑터를 학습했다. batch 1, iterations 20, LoRA 4 layers/rank 8, learning rate 1e-5 등은 초기 시험과 같다. 20-step은 63개 학습 행 전체를 한 번씩 학습한 것이 아니다. 설정·inspection·10/20-step 및 최종 어댑터 저장을 확인했다.

콘솔 validation loss는 1-step 0.466, 10-step 0.035, 20-step 0.036이었다. `val_batches=2`의 소규모 손실이며, 낮아진 loss만으로 생성 응답의 개선이나 최적 체크포인트를 판단하지 않는다. 10-step 어댑터의 생성 응답은 비교하지 않았다.

## 후속 검수본 시험: 비교 결과와 남은 오류

동일한 검증 13행으로 기본 모델과 새 최종 어댑터를 비교했다. 모델·토크나이저·프롬프트·입력·temperature 0·seed 42·출력 상한 512토큰을 고정했다. 데이터 및 최종 어댑터 해시가 비교 manifest와 일치하고 before/after의 행 순서·완료 수가 일치함을 확인했다.

| 지표 | BEFORE | AFTER |
|---|---:|---:|
| 실험 action 검증기 통과 | 13/13 (100%) | 13/13 (100%) |
| 검증기 통과 및 action 종류 일치 | 7/13 (53.8%) | 7/13 (53.8%) |
| 정답 JSON 전체 일치 | 5/13 (38.5%) | 5/13 (38.5%) |

전체 일치 기준 개선 0건·퇴보 0건이다. 출력이 모두 같다는 뜻은 아니다. 한 수정 요청은 BEFORE의 조회 전 가상 ID 사용에서 AFTER의 조회 전 `SELECT_TARGET`으로 바뀌었지만 둘 다 잘못된 단계다. 별도 제어부나 동적 schema 제약 없이 생성했으므로 형식 통과를 실행 가능한 정답으로 해석하지 않는다.

AFTER의 전체 불일치 8행은 다음과 같다.

| 분류 | 행 수 | 해석 |
|---|---:|---|
| 날짜 질문의 표현 차이 | 2 | 의미상 적절한 날짜 질문이나 JSON 문자열 전체 일치는 실패. BEFORE도 같은 종류의 차이 |
| 날짜 미확인 상태에서 CREATE | 2 | 날짜 질문 대신 기준일을 사용해 등록하려 함 |
| 등록 정보가 모두 확인됐는데 LIST | 2 | 등록 대화의 의도를 후속 턴에서 유지하지 못함 |
| 조회 전에 SELECT_TARGET | 2 | 수정·삭제 대상 조회를 건너뜀 |

핵심 보완 대상은 출력 형식보다 질문 필요 여부, 등록 의도 유지, 조회→대상 선택·확인 순서다. validation의 오답·정답을 train에 복사하지 않고, 기존 train의 해당 유형과 변형 범위를 점검한 뒤 학습량을 늘려 동일 조건으로 재평가한다. 잠근 test와 전체 대화 성능 평가는 아직 수행하지 않았다.

기존 후속 비교 summary의 `scope`에는 도구에 남은 고정 문구 `UNREVIEWED`가 기록돼 있다. 실제 입력은 준비 결과의 `REVIEWED_SMOKE_ONLY` 및 승인본 해시와 일치한다. 원본 로그는 보존하고 공유 집계에 정정 근거를 기록했다. 공유 도구는 새 비교부터 준비 결과의 검수 상태를 표시한다.

## 기존 77.5%와 비교할 수 없는 이유

기존 31/40건은 이전 프롬프트·제어부에서 동적 JSON schema와 가드를 포함해 평가한 대화 시나리오 단위의 잠정 일치율이다. 이번 43/114건은 새로운 프롬프트의 고정 문맥에서 출력 제약 없이 생성한 개별 응답의 JSON 전체 일치다. 분모, 런타임, 출력 제약, 버전과 채점 기준이 다르므로 성능 하락으로 해석하거나 같은 그래프의 전후 값으로 사용하지 않는다.

## 한계와 다음 단계

1. 초기 미검수 시험과 30개 시범 승인본 시험을 완료했다. 전체 데이터 검수·학습 완료가 아니며 사용자 위임 검수는 독립 검수와 구분한다.
2. 정답·프롬프트·입력 문맥을 먼저 점검하고 모델 오류와 데이터 오류를 구분한다. 모델 출력을 정답으로 복사하지 않는다.
3. 검수한 train/validation으로 전체 학습을 진행하고 validation 결과로 학습량·체크포인트를 선택한다.
4. 최종 평가는 같은 출력 제약·제어부·채점 기준을 적용한 시스템 평가로 수행한다. test 초안은 독립 시험본으로 검수·고정하기 전까지 최종 성능 주장에 사용하지 않는다.
5. 이번 실행 당시 모델 저장소 revision과 전체 환경 lockfile은 기록하지 않았다. 실행 버전과 데이터·어댑터 해시는 보존했으나 비트 단위 재현성은 보장하지 않는다.
