## 1. 분석 목적과 전제

학습용 자료와 평가 코드의 기준을 비교하고, 초기 모델 응답에서 나타난 오류를 분석하여 다음 데이터 정비 방향을 제시한다.

이번 평가는 Python 코드의 `TESTS`에 정의한 100개 문항으로 수행하였다. 기존 학습 60건·검증 20건 자료는 라벨 규칙을 비교하기 위한 참고 자료로 검토했으며, 이번 평가 코드의 입력으로 사용하지 않았다. 이 평가 코드에는 해당 자료로 모델을 학습시키는 과정이 없으므로, 이번 결과를 해당 자료로 파인튜닝한 결과로 설명하지 않는다. 또한 기존 자료와 평가 문항이 서로 중복되지 않는다는 검증을 완료한 것은 아니다. 관찰된 모델 오류를 기존 학습 자료 때문에 발생한 문제로 단정하지 않는다.

## 3. 데이터 및 규칙에서 확인한 문제

### 3.1 카테고리 기준 불일치

| 기준 자료 | 카테고리 |
| --- | --- |
| 수행계획서·첨부 학습 자료 | 재고·반품·회의·개인·기타 |
| Schedule API | `INVENTORY`, `RETURN`, `MEETING`, `PERSONAL`, `OTHER` |
| 초기 평가 코드 | 반품·재고·입고·피킹·출고 |

초기 평가의 카테고리 일치율 99%는 코드가 정한 임시 분류에 대한 결과다. 프로젝트에서 사용하는 5개 카테고리의 분류 성능으로 해석할 수 없다. 첨부 학습 자료의 `입고 물품 점검`은 재고로 분류되어 있으나, 초기 평가 코드는 입고를 독립 분류로 사용한다.

보완 방향: 수행계획서와 API를 기준으로 분류를 통일하고, 입고·출고·피킹 업무를 어느 분류로 처리할지 팀 규칙을 정한 뒤 문항과 정답에 반영한다. 한국어 라벨과 API enum 사이의 변환도 명시한다.

### 3.2 출력 표현 방식 불일치

| 항목 | 첨부 학습 자료 | 초기 평가 코드 |
| --- | --- | --- |
| 외부 형식 | `<schedule>…<schedule_end>` | JSON 객체 |
| 명령 | `command` | `intent` |
| 날짜 | `date_expr="내일"` 등 원문 표현 | `date="2026-09-26"` 등 실제 날짜 |
| 업무 내용 | `title="재고 확인"` | `category="재고"`, `content="확인"` |
| 추가 조건 | `period`, `time_offset`, `new_date_expr`, `missing` 등 | 고정된 6개 필드 |

`api.md`는 AI 서비스 요청·응답 형식과 상대 날짜 해석 등을 미확정 사항으로 두고 있다. 따라서 첨부 자료의 schedule 형식이 최종 확정 규격이라고 볼 수 없다. 또한 Schedule REST API의 요청 형식과 LLM 중간 출력은 역할이 다르므로 무조건 동일하게 만들 필요는 없다.

보완 방향: LLM 중간 출력과 백엔드 요청 사이의 변환 책임을 합의한다. 이후 학습 자료, 프롬프트, 정답, 평가 코드를 같은 규칙으로 정비한다.

현재 평가의 `location`은 Schedule API 및 DB에 독립 필드로 정의되어 있지 않다. 장소 추출을 내부 실험으로 평가할 수는 있지만, 저장·연동 방식은 별도 합의가 필요하다. 또한 Schedule DB는 LLM 프롬프트·응답과 대화 문맥을 저장하지 않으므로 평가 결과 CSV의 관리와 Schedule DB 저장은 별도로 취급한다.

### 3.3 평가 기능의 누락

첨부 라벨 자료는 등록·조회·수정·삭제·완료·재질문을 포함하지만, 초기 평가 코드는 앞의 4개 의도만 허용한다. 정보 부족 시 `clarify`를 사용하도록 한 자료의 규칙을 평가할 수 없다.

예를 들어 `그거 삭제해`는 이전 대화나 대상 일정 정보가 없는 상태에서 삭제할 대상을 특정할 수 없다. 현재는 delete 의도와 null 필드를 정답으로 두었으므로, 의도 추출은 평가할 수 있어도 적절한 재질문 여부는 평가하지 못한다.

보완 방향: 의도 인식과 실행 가능 여부를 구분하고, 완료·재질문 문항 및 필요한 문맥 정보를 제안한다. API의 완료 처리는 `completed` 수정으로 정의되어 있지만, LLM이 이를 표현할 명령 이름과 재질문 형식은 관련 담당자와 합의한 뒤 공통 규칙으로 적용한다.

### 3.4 프롬프트와 정답 설명의 차이

조회 문항의 content 정답을 `일정 조회`로 둔 사례가 많지만 프롬프트에는 해당 값을 사용하라는 설명이 없다. 수정 요청에서도 변경 후 값을 출력한다는 규칙이 충분히 명시되어 있지 않다.

보완 방향: 조회 시 content 처리, 명령 표현 제거, 카테고리 단어 중복 금지, 수정 대상과 변경 값 구분을 문서화한다. 예시는 평가 문항을 그대로 사용하지 않는 별도 예시로 제공한다.

### 3.5 질문 목록의 버전 차이

별도 `qwen_test_questions_100.csv`와 채점 코드 내부의 `TESTS`에는 서로 다른 문항이 존재한다. 해당 CSV를 이번 실행의 입력 파일이라고 설명하면 실제 실행 내용과 일치하지 않는다.

보완 방향: 문항 ID, 발화, 정답, 기준 날짜, 규칙 버전을 한 평가 데이터 파일에서 관리하고 코드가 이를 읽도록 통일한다. 이번 기록은 실행 코드와 결과 CSV를 기준으로 보존한다.

## 4. 모델 응답에서 관찰한 오류

아래 번호는 [`qwen_100_scored_results.csv`](../datasets/qwen/v0.1_initial/qwen_100_scored_results.csv)의 번호다. 정답은 초기 평가 코드의 기준을 따른다.

| 번호 | 사용자 발화 | 정답과 실제 출력의 차이 | 관찰 내용 |
| --- | --- | --- | --- |
| 3 | 모레 오후 2시에 C구역 입고 정리 추가해줘 | date: `2026-09-27` → `2026-09-26` | 상대 날짜 해석 오류 |
| 52 | 내일 오전 9시 C구역 입고 정리를 오전 10시로 변경해줘 | time: `10:00` → `09:00` | 변경 전 시간을 출력 |
| 72 | 오늘 오후 6시 B구역 출고 검수를 내일 오전 9시로 바꿔줘 | date/time: `2026-09-26 09:00` → `2026-09-25 18:00` | 변경 전 날짜와 시간을 출력 |
| 1 | 오늘 오후 3시에 B구역 반품 확인 등록해줘 | content: `확인` → `확인 등록` | 명령 표현이 업무 내용에 포함 |
| 2 | 내일 오전 9시에 A구역 재고 조사 넣어줘 | content: `조사` → `재고 조사` | category 단어 중복 |
| 40 | 내일 C구역에 뭐 해야 해 | intent: `read` → `create`, category: null → `피킹` | 의도 오인 및 입력에 없는 분류 생성 |
| 30 | 내일 오전 일정 조회해줘 | time: null → `00:00` | 시간대를 특정 시각으로 변환 |

`content` 일치율은 27%, 날짜 일치율은 72%였다. content의 낮은 수치에는 실제 추출 오류뿐 아니라 규칙 설명 부족과 엄격한 문자열 비교의 영향도 포함된다. 이 수치만으로 모델의 전반적인 언어 이해 성능을 판단하지 않는다.

## 5. 평가 시스템의 한계

### 5.1 null 타입 오류를 허용하는 정규화

응답 35건에서 실제 JSON null 대신 문자열 `"null"`을 사용했다. 현재 normalize 함수는 두 표현을 같게 처리한다. 완전 정답 16건 중 41·55·67·87번도 문자열 `"null"`을 포함한다.

보완 방향: 원문 기준의 형식 검사와 정규화 후 내용 평가를 분리한다. 현재 16%를 엄격한 출력 규격 준수율로 보고하지 않는다.

### 5.2 필수 키와 값 검증 부족

현재 코드는 `result.get(field)`를 사용하므로 키가 없는 경우와 값이 null인 경우를 구분하지 못한다. 이번 응답 100건에는 모두 6개 키가 있었지만, 평가기 자체에는 필수 키·추가 키·허용값·날짜 및 시간 형식 검사가 필요하다.

보완 방향: JSON 파싱 성공, 필수 키 및 타입 준수, 의미 정확도를 별도 지표로 기록한다. 실행 실패 시에는 원문과 예외 원인을 보존한다.

### 5.3 기간과 수정 대상 표현의 한계

고정된 date·time만으로는 `오전`, `오후 3시 이후` 등의 조건을 충분히 표현할 수 없다. 또한 변경 후 값만 저장하면 어떤 기존 일정을 수정해야 하는지에 대한 정보가 손실될 수 있다.

보완 방향: 기간 조건과 수정 대상·변경 값을 분리하는 표현을 팀과 합의한 뒤 정답 구조를 확장한다. Schedule API를 통한 일정 조회와 수정·삭제 대상 선택까지 검증하는 통합 테스트는 연동 계약 합의 후 별도로 구성한다. AI가 Schedule DB에 직접 접근하는 방식은 사용하지 않는다.

### 5.4 성능 해석과 재현성의 한계

- 항목별 일치율에는 null끼리 맞은 사례가 포함되어 있다. 향후 정보가 실제로 존재하는 문항의 정확도도 구분한다.
- 부분 정답은 1개만 맞아도 부여된다. 부분 정답 84건을 업무 처리 성공 84건으로 해석하지 않는다.
- 모델 digest, 실행 환경 버전, 생성 옵션, 응답 시간 및 반복 실행 결과가 기록되어 있지 않다.
- 첨부 학습·검증 자료와 평가 문항 사이의 중복·유사 문장 검사는 별도 수행이 필요하다.

## 7. 현재 판단

100건의 초기 평가와 자동 채점 체계를 통해 날짜 처리, 변경 값 추출, 업무 내용 정제 및 출력 타입 관련 문제를 확인하였다. 동시에 프로젝트 자료와 평가 코드의 분류·표현 기준이 달라 평가 기준 정비가 선행되어야 함을 확인하였다.

다음 단계에서는 기존 초기 평가 기록을 보존하고, 합의된 규칙으로 평가셋과 코드를 정비한다. 평가 기준 변경에 따른 점수 차이와 실제 모델·프롬프트 개선 효과를 구분하며, 동일 조건의 비교 결과가 확보되기 전에는 성능 향상을 단정하지 않는다.

전체 측정 수치와 평가 환경은 `dataset_evaluation.md`에 정리한다.
