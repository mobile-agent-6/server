## 1. 목적과 평가 범위

사용자의 일정 관련 텍스트를 Qwen이 구조화된 정보로 변환할 수 있는지 확인하기 위해 평가 문항 100개와 자동 평가 코드를 구성하였다. 각 문항의 예상 정답과 모델 응답을 비교하고 결과를 CSV로 저장하였다.

이번 평가는 텍스트 입력부터 LLM 출력까지를 대상으로 한다. STT 음성 인식, TTS, 실제 일정 DB 조작, 모바일 앱 연동 및 Orange Pi 실기기 성능은 평가 범위에 포함하지 않았다. 현재 결과는 초기 성능 측정이며, 프롬프트 개선 또는 파인튜닝 전후의 성능 향상을 검증한 결과는 아니다.

## 2. 평가 환경 및 설정

| 항목 | 설정 |
| --- | --- |
| 모델 지정값 | `qwen3:4b` |
| 모델 호출 | 로컬 Ollama의 `http://localhost:11434/api/generate` |
| 실행 코드 | [`datasets/qwen/v0.1_initial/qwen_batch_test_100_scored.py`](../datasets/qwen/v0.1_initial/qwen_batch_test_100_scored.py) |
| 구현 언어 | Python |
| 상대 날짜 기준 | `2026-09-25` |
| 출력 설정 | `format="json"`, `think=false`, `stream=false` |
| 요청 제한 시간 | 문항당 300초 |
| 평가 단위 | 문항별 독립 요청, 이전 대화 이력 미제공 |

모델 이름과 호출 설정은 실행 코드에 근거한다. 실행 장비의 상세 사양, Python·Ollama 버전, 모델 digest, 응답 시간은 현재 결과 파일에 기록되어 있지 않다. 재현성을 높이기 위해 다음 평가부터 기록할 예정이다. 작성일과 상대 날짜 해석의 기준일은 서로 다르다.

## 3. 평가 데이터셋 구축

### 3.1 문항 구성

| 유형 | 정답 intent | 문항 수 |
| --- | --- | --- |
| 등록 | `create` | 25 |
| 조회 | `read` | 25 |
| 수정 | `update` | 25 |
| 삭제 | `delete` | 25 |
| 합계 |  | 100 |

실제 평가셋은 Python 코드의 `TESTS` 목록이다. 각 문항에 사용자 발화와 6개 항목의 예상 정답을 정의하였다. 오늘·내일·모레·다음 주 등의 날짜 표현, 오전·오후와 분 단위 시간, 장소, 일정 변경 및 대상이 모호한 삭제 요청 등을 포함한다. 삭제 25건에는 문맥·대상이 모호한 사례 5건이 포함되어 있다.

별도 파일 `qwen_test_questions_100.csv`는 코드 내부 문항과 일부 다르므로 이번 실행의 기준 데이터셋으로 사용하지 않는다. 이번 평가의 문항과 정답은 실행 코드와 결과 CSV를 기준으로 확인한다.

### 3.2 출력 및 정답 필드

| 필드 | 이번 평가의 기준 |  |
| --- | --- | --- |
| `intent` | 등록·조회·수정·삭제 의도 |  |
| `date` | 기준일을 반영한 `YYYY-MM-DD` 또는 null |  |
| `time` | `HH:MM` 또는 null |  |
| `location` | A구역·B구역·C구역 등의 장소 또는 null |  |
| `category` | 반품·재고·입고·피킹·출고 또는 null |  |
| `content` | 업무 내용. category 단어를 중복하지 않는 것을 기준으로 설정 |  |

이번 카테고리는 초기 평가에 사용한 분류이며, 수행계획서와 Schedule API의 재고·반품·회의·개인·기타와 차이가 있다. 프로젝트 기준에 맞춘 문항·정답·프롬프트 정비가 필요하다.

현재 6개 필드는 초기 평가용 LLM 출력이며 Schedule API 요청 형식이 아니다. 특히 `location`은 현재 Schedule API와 DB에 독립 필드로 정의되어 있지 않다. 장소 정보의 활용·저장 방식은 팀 협의가 필요하며, 평가 결과를 근거로 API나 DB 필드를 임의로 추가하지 않는다.

## 4. 자동 평가 시스템

평가 코드는 다음 순서로 실행된다.

1. `TESTS`에서 사용자 발화와 예상 정답을 읽는다.
2. 기준 날짜와 출력 규칙을 포함한 프롬프트를 작성한다.
3. 로컬 Ollama를 통해 Qwen에 요청한다.
4. 응답 원문을 JSON으로 해석하고 6개 필드를 추출한다.
5. 각 필드를 정답과 비교하여 문항별 결과를 저장한다.
6. 전체 결과와 항목별 일치 수를 요약 CSV에 저장한다.

| 판정 | 기준 |
| --- | --- |
| 정답 | 6개 항목 모두 일치 |
| 부분 정답 | 1~5개 항목 일치 |
| 오답 | 0개 항목 일치 |
| 실행 실패 | 요청·응답 해석 등의 과정에서 예외 발생 |

문자열 앞뒤 공백을 제거하고 빈 문자열, 문자열 `"null"`, 문자열 `"none"`을 Python의 `None`으로 정규화한 뒤 비교한다. 따라서 현재 채점은 엄격한 출력 형식 검사가 아니라 정규화 후 값의 일치 검사다. `content`는 의미 유사도 평가 없이 문자열 일치로 채점한다.

## 5. 초기 성능 측정 결과

### 5.1 전체 결과

| 지표 | 건수 | 비율 |
| --- | --- | --- |
| 총 평가 문항 | 100 | 100% |
| 정상 실행 | 100 | 100% |
| 완전 일치 | 16 | 16% |
| 부분 일치 | 84 | 84% |
| 0개 항목 일치 | 0 | 0% |
| 실행 실패 | 0 | 0% |

응답 원문 100건을 재검토한 결과 모두 JSON 파싱에 성공했고, 모두 지정된 6개 키를 포함하였다. 단, 이는 값의 타입·표현 규칙과 의미까지 모두 정확하다는 뜻은 아니다. JSON 모드를 사용한 조건에서의 결과다.

### 5.2 항목별 결과

항목별 일치율은 해당 항목의 일치 건수를 전체 문항 100건으로 나눈 값이다. 정답과 출력이 모두 null인 사례도 일치로 포함한다.

| 항목 | 일치 건수 | 일치율 |
| --- | --- | --- |
| intent | 98 | 98% |
| date | 72 | 72% |
| time | 93 | 93% |
| location | 99 | 99% |
| category | 99 | 99% |
| content | 27 | 27% |

의도·장소·분류는 이번 정답 기준에서 높은 일치율을 보였다. 날짜와 업무 내용은 상대적으로 낮았으며, 특히 업무 내용에는 명령 표현이나 카테고리 단어가 함께 포함되는 사례가 관찰되었다. 모든 수치는 현재 임시 평가셋과 채점 방식에 한정된다.

### 5.3 의도별 완전 일치

| 유형 | 문항 수 | 완전 일치 건수 | 완전 일치율 |
| --- | --- | --- | --- |
| 등록 | 25 | 6 | 24% |
| 조회 | 25 | 1 | 4% |
| 수정 | 25 | 4 | 16% |
| 삭제 | 25 | 5 | 20% |

조회 문항은 정답 content를 `일정 조회`로 둔 사례가 많으나, 해당 표현을 사용하라는 규칙이 프롬프트에 명시되어 있지 않다. 낮은 조회 완전 일치율을 모델의 조회 의도 이해 부족만으로 해석하지 않는다.

## 6. 성능 개선 진행 상태

| 구분 | 현재 상태 |
| --- | --- |
| 평가 데이터셋 및 자동 채점 코드 | 구축 완료 |
| 100건 초기 평가 | 수행 완료 |
| 결과 검토 및 주요 문제 식별 | 완료 |
| 프로젝트 카테고리 적용 및 AI 출력 규칙 협의 | 예정 |
| 프롬프트 보완 후 재평가 | 예정 |
| 파인튜닝 및 개선 전후 비교 | 이번 보고서에서 수행·검증하지 않음 |

현재 확인된 성과는 평가 체계 구축과 초기 성능 측정이다. 성능 향상 수치는 아직 제시하지 않는다. 문자열 `"null"`을 사용한 응답이 35건이며, 현재 완전 정답 16건 중 4건에도 이 문제가 포함되어 있어 향후 형식 검사와 내용 검사를 분리할 예정이다.

## 7. 다음 평가 계획

1. 수행계획서·Schedule API에 명시된 5개 카테고리를 문항과 정답에 반영한다. 입고·출고·피킹 등의 세부 업무 매핑은 관련 담당자와 확인한다.
2. 팀 협의를 통해 LLM 출력 필드, 날짜 해석 책임, 수정 대상과 변경 값의 표현을 확정한다.
3. 완료·재질문, 시간대·기간 조건의 평가 문항을 제안하고, 관련 담당자와 출력 규칙을 합의한 뒤 공통 평가에 반영한다.
4. 프롬프트에 정답 작성 규칙을 명확히 설명하고 형식 검사를 추가한다.
5. 정비된 평가셋을 고정한 뒤 기준 실행과 개선 실행을 비교한다.
6. 반복되는 오류를 분석한 후 추가 학습 데이터와 파인튜닝 필요성을 검토한다.

문항 또는 채점 기준이 달라진 결과는 기존 16%와 직접 비교하여 모델 성능 향상으로 보고하지 않는다.
