# Qwen 멀티턴 데이터셋·파인튜닝·전후 평가 계획

> 작성일: 2026-10-10
> 현황 확인: 2026-10-12. **평가·학습 계획은 제안 상태**다. 아래의 Qwen validation 결과는 미검수 정답에 대한 잠정 측정이며, 학습이나 잠근 test의 전후 비교 결과가 아니다.
> 범위: 이정민 페르소나의 일정 비서, 맥북 로컬 Qwen 실험, 이후 Orange Pi 적용성 확인.
> 관련 계약: AI 출력·대화 상태·Schedule API 연동은 `TBD-AI`, 평가 데이터 세부 schema와 검수 방식은 `TBD-DATA`, 최종 데이터 위치는 `TBD-TEAM`이다. 이 문서만으로 공유 계약을 확정하지 않는다.

## 1. 목표와 비교선

목표는 **파인튜닝 이후 멀티턴 일정 대화가 실제로 개선됐는지** 같은 시험으로 확인하는 것이다. 주 비교는 두 실행뿐이다.

| 구분                            | BEFORE                      | AFTER                              |
| ------------------------------- | --------------------------- | ---------------------------------- |
| 모델                            | 기본 Qwen                   | 같은 기반 체크포인트 + LoRA 어댑터 |
| 시스템 프롬프트                 | 고정된 멀티턴 프롬프트`P` | 동일한`P`                        |
| 평가 문제·채점·대화 실행기    | 고정                        | 동일                               |
| 장비·런타임·양자화·생성 설정 | 고정                        | 가능한 한 동일                     |

프롬프트 개선은 **학습 전의 별도 실험**으로 다룬다. `train`·`valid` 자료로 `P`를 정한 뒤 잠근 `test`에서는 바꾸지 않는다. 현재 6필드 단일 발화 프롬프트와 과거 v0.1의 16/100은 멀티턴 BEFORE 점수가 아니다. 단일 발화 평가를 계속한다면 별도 표로 보고한다.

```text
시나리오 작성·검수 → train/valid/test 분리 → 출력·채점 규칙 고정
→ 기본 Qwen 기준 측정 → LoRA 학습 → 같은 test 재측정
→ 사례별 변화·안전·시간·토큰 비교와 별도 사람 검토 → Orange Pi 별도 검증
```

## 2. 현재 출발점

- 현재 [100문항](../datasets/qwen/experiments/api_categories/cases_100.jsonl), [프롬프트](../datasets/qwen/experiments/api_categories/prompt.txt), [실행기](../datasets/qwen/tools/run_qwen_eval.py), [채점기](../datasets/qwen/tools/qwen_eval.py)는 **단일 발화 → 6필드 JSON**을 평가한다. 정답은 `proposed_unreviewed` 상태다.
- 이 100문항을 새 멀티턴 LoRA에 **6필드 출력 그대로 넣지 않는다**. 재사용할 사례는 새 action 출력으로 다시 정답을 만들고 검수·분리한다. 멀티턴 test와 겹치는 발화·시나리오는 학습에 넣지 않는다.
- 단일 발화 데이터에는 `location`이 있으나 Schedule API에는 독립 위치 필드가 없다. 새 멀티턴 출력·평가에서는 별도 위치 데이터를 만들지 않는다. “B구역 재고 확인”처럼 **대화에서 구역을 언급하는 것은 허용**한다. 구역명을 일정 제목에 자동 삽입하는 규칙도 두지 않는다.
- [Schedule API](api.md)는 조회·생성·수정·삭제와 `INBOUND`, `INVENTORY`, `OUTBOUND`, `RETURN`, `OTHER`를 정의한다. 생성 요청에는 `title`, `scheduledAt`, `category`, `reminderMinutesBefore`가 필요하고, `10`은 10분 전 알림이다. POST에는 `Idempotency-Key`가 필요하다.
- [AI 영역 로컬 시범 구현](../ai/README.md)에 action 검증, 한 세션의 대화 상태, Ollama `/api/chat`와 기존 Schedule HTTP API 연결이 있다. [초기 멀티턴 시범 자료](../datasets/qwen/experiments/multiturn_pilot/README.md)의 미검수 예시 5건에 이어, [멀티턴 400건 초안](../datasets/qwen/experiments/multiturn_400_v0.1/README.md)이 train 260·validation 40·test 예약 100건으로 만들어졌다. DATA 내부 초안의 다중 후보 60건은 ID 없는 `SELECT_TARGET` 제안으로 고쳤고 정답 재생은 400/400건 통과했다. 이전 규칙에서 실제 Qwen은 미검수 validation 40건 중 31건 잠정 일치했으며, 이는 새 규칙의 측정값이 아니다. 30건 검수 표본(train 25·validation 5)은 이전 정답 재생 30/30건 통과했지만 사람 승인 0건이다. 검수 원본 보존 도구·잠정 평가기·로컬 HTML 검토 화면이 있으며, 검수된 평가셋·확정 채점 기준·합의된 출력 계약은 아직 없다. 맥북에서의 MLX 20-step 시험 학습과 고정 문맥 응답 비교는 [2026-10-16 결과 보고서](qwen_smoke_training_results_20261016.md)에 기록했다. 본 계획의 검수·전체 학습·시스템 전후 평가를 완료한 것은 아니며, Orange Pi 성능도 아직 측정하지 않았다.

## 3. 단계와 산출물

| 단계         | 작업                                                     | 완료 판단·산출물                                                    |
| ------------ | -------------------------------------------------------- | -------------------------------------------------------------------- |
| 0. 계약 제안 | action 출력, 대화 상태, 확인 후 실행, API 변환 규칙 작성 | AI·BE·DATA 검토용 제안. 공유 인터페이스 확정은 관련 담당자 합의 후 |
| 1. 데이터    | 현장 대화 시나리오 작성, 정답 검수, 누출 없는 분리       | 버전이 지정된`scenarios_*.jsonl`, 검수 기록, 중복 점검             |
| 2. 평가기    | 대화 이력 재생, 모의 Schedule, 차례별 로그·자동 채점    | 정상·오류·거절 분기를 검증한 로컬 실행기와 사람 검토 기준           |
| 3. 기준 측정 | 기본 모델에 고정 프롬프트`P`와 잠근 test 실행          | BEFORE 결과와 모델·환경·데이터 해시                                |
| 4. 학습      | train을 chat 학습 행으로 변환, LoRA 학습, valid 점검     | 어댑터·학습 설정·검증 손실·실패 기록                              |
| 5. 재측정    | 같은`P`·test·채점으로 AFTER 실행                     | 두 결과의 사례별 차이, 품질·안전·시간·토큰 표와 별도 사람 검토 기록 |
| 6. 배포 검토 | 후보 모델 형식과 Orange Pi 런타임 확인                   | 실기기 속도·메모리·오프라인 동작의 별도 결과                       |

단계 0의 공유 계약이 미확정이어도 **모의 일정 저장소를 사용하는 DATA/AI 내부 실험**은 제안 상태로 진행할 수 있다. AI 영역의 로컬 Schedule HTTP 연결은 시범 구현됐으며, 공개 AI endpoint·상태 관리·재시도 규칙 등 공유 연동 계약은 합의 후 확정한다.

## 4. 데이터셋 설계

### 4.1 파일과 분리 단위

UTF-8 `.jsonl`을 사용한다. JSON 객체 하나가 파일 한 줄이다. 예시는 읽기 쉽게 줄바꿈했다.

| 파일                                                   | 한 줄의 단위                         | 목적                                      |
| ------------------------------------------------------ | ------------------------------------ | ----------------------------------------- |
| `scenarios_train.jsonl`                              | 대화 시나리오 1건                    | 학습 자료의 원본                          |
| `scenarios_valid.jsonl`                              | 대화 시나리오 1건                    | 프롬프트·학습 설정 개발 점검             |
| `scenarios_test.jsonl`                               | 대화 시나리오 1건                    | 잠근 전후 비교 시험                       |
| `train.jsonl`, `valid.jsonl`                       | 한 assistant 응답 시점의`messages` | 선택한 학습 도구의 입력으로 원본에서 변환 |
| `turn_results.jsonl`, `summary.json` 또는 `.csv` | 실제 차례별 결과·집계               | 실행 기록. 모델 출력과 시간·토큰 포함    |

표의 이름은 계획상 산출물이다. 현재 v0.1 초안은 [`multiturn_400_v0.1/`](../datasets/qwen/experiments/multiturn_400_v0.1/README.md)의 `train/`, `validation/`, `test/` 아래 `scenarios_UNREVIEWED.jsonl`로 관리하며, 검수 후 별도 `scenarios_REVIEWED.jsonl`을 출력한다. 현재 생성된 학습 행도 미검수 후보이고 학습에 투입하지 않는다.

**대화 계열 단위로 분리**한다. 한 시나리오의 첫 질문은 train, 후속 답변은 test에 넣지 않는다. 같은 시작 대화에서 갈라진 승인·거절 분기와 같은 일정 설정의 어휘 변형에는 공통 `conversation_group_id`를 부여해 반드시 같은 split에 둔다. split 전 그룹 중복·유사도 점검 결과를 기록한다. test 정답과 실제 오류 사례를 보고 학습 문장을 고친 경우에는 그 test를 더 이상 독립 시험으로 간주하지 않는다. 새로운 잠근 test가 필요하다.

**첫 버전의 작성 목표 400건은 미검수 초안 수량으로 채웠다.** 아래 행동별 균형은 원래 계획이며, 초안의 실제 분포와 승인 상태는 별개다.

| 분리           |   시나리오 수 | 등록·조회·수정·삭제 | 용도                                               |
| -------------- | ------------: | ---------------------: | -------------------------------------------------- |
| train          |           260 |                각 65건 | 검수·승인 뒤 LoRA 학습 후보. 현재 시범 표본 25건 포함 |
| valid          |            40 |                각 10건 | 프롬프트와 학습 설정 선택                          |
| test 예약 초안 |           100 |                각 25건 | 검수·기준 고정 뒤 잠근 BEFORE/AFTER 시험으로 전환  |
| **합계** | **400** |     **각 100건** | 서로 다른 대화 시나리오 기준                       |

현재 초안의 train 등록·조회·수정·삭제는 각각 72·61·64·63건으로 원래 목표인 각 65건과 다르다. validation은 각 10건, test 예약 초안은 각 25건이다. 30건 시범 표본은 train 25건·validation 5건에서 골랐으며 전체 400건에 추가되는 수량이 아니다. 사람 승인 사례는 0건이다. train 시나리오 한 건에서 assistant 학습 행이 여러 개 나오므로 학습 행 수는 대화 260건보다 많고, 실제 대화 길이에 따라 정해진다. test 100건은 실패·재시도 사례와 의미상 유사성까지 검수한 뒤 BEFORE 실행 전에 잠근다. 전체 비율과 함께 `성공 건수/시험 건수`, 유형별 분모를 보고한다. 자료 작성 여건에 따라 목표 수를 조정한다면 test를 열어 보기 **전에** 계획 버전을 수정한다.

### 4.2 포함할 장면

| 기능      | 대표 사례                                                      |
| --------- | -------------------------------------------------------------- |
| 추가 질문 | 날짜·시각 누락, 어느 일정인지 모호함, 두 후보 중 선택         |
| 확인      | 수정·삭제 승인, 거절, 확인 중 정정, 다른 요청으로 전환        |
| 업무      | 재고 실사·부족 수량, 피킹, 반품, 입고, 교대 인수인계·회의    |
| 일정      | 오늘·내일·야간 교대, 시간 변경, 10분 전 알림, 알림 해제      |
| 대화      | 조회 뒤 “그건?”, 짧은 음성식 발화, 인식 오류를 사용자가 정정 |
| 오류      | 빈 조회 결과, API 오류·시간 초과, 유효하지 않은 Qwen JSON     |

현재 400건 초안의 기대 응답에는 `error`·`stale`이 없고 API 실패·응답 유실·재시도 주입 사례도 없다. 오류 행은 위 설계 범위에 남아 있으며 test를 잠그기 전에 작성·검수해야 한다.

카테고리는 API의 다섯 영문 enum으로만 채점한다. 피킹은 `OUTBOUND`, 재고 실사와 재고 부족 수량 확인은 `INVENTORY`, 반품은 `RETURN`이다. 구역 표현은 사용자 발화에 나타날 수 있지만 별도 위치 필드나 구역 정확도 지표는 만들지 않는다.

### 4.3 평가 시나리오 예시 — 제안 schema

```json
{"id":"ask-time-001","conversation_group_id":"ask-time-family-001","reference_datetime":"2026-10-10T09:00:00+09:00","initial_schedules":[],"turns":[{"user":"내일 B구역 재고 확인 등록해줘","expect":{"model_actions":["ASK"],"reply_kind":"ask","missing":"time","writes":0}},{"user":"오전 10시","expect":{"model_actions":["CREATE"],"reply_kind":"created","post_body":{"title":"재고 확인","scheduledAt":"2026-10-11T10:00:00+09:00","category":"INVENTORY","reminderMinutesBefore":null},"writes":1}}],"label_status":"proposed_unreviewed"}
```

`model_actions`는 사용자 턴 안의 실제 모델 호출 순서를 기록하는 **진단용 기대값**이다. `LIST` 뒤 같은 턴에 한 번 더 호출하면 두 action을 기록하고, 제어부가 직접 처리하는 번호 선택·승인·거절·등록 재시도 턴은 빈 배열 `[]`을 기대할 수 있다. 모델 호출 순서의 단순한 차이만으로 주 지표를 실패 처리하지 않는다. 단, 승인 전 쓰기 금지처럼 안전·API 계약에 필요한 순서와 모델 출력 JSON 유효성은 엄격히 검사한다. `writes`는 성공한 변경 수가 아니라 실제 POST·PATCH·DELETE HTTP **시도 횟수**이며, 적용된 변경은 최종 상태로 따로 확인한다. 턴마다 표시된 응답, GET·POST·PATCH·DELETE 호출의 필수 순서·대상·본문·키, 최종 일정 상태를 채점한다. 오류 사례에는 요청별 503·timeout·응답 유실 주입과 턴별 시각 경과도 기록한다. 허용할 다른 대화 경로·API 재시도 범위는 시범 검수에서 기록하고 잠근 test 실행 전에 고정한다. 위 필드명은 `TBD-DATA` 제안이며 평가기와 함께 검수한다.

수정 승인과 거절은 같은 시작 발화를 쓰더라도 **별도 시나리오**로 만들고 같은 `conversation_group_id`로 묶는다. 초기 일정 fixture에는 실제 Schedule 응답에 필요한 `id`, `title`, `scheduledAt`, `category`, `completed`, `reminderMinutesBefore`, `createdAt`, `updatedAt`을 둔다. `reminderAt`은 모의 API가 계산한다. 승인 전에는 쓰기 0회, 거절 후에도 0회, 정상 응답 경로의 승인 후에는 정해진 ID에 PATCH 1회가 발생해야 한다. timeout·503 재시도 사례에서는 같은 ID·본문의 요청 횟수와 실제 적용 결과를 별도로 채점한다.

### 4.4 학습 행 예시 — 도구 형식은 선택 후 검증

실제 **모델 호출**마다 이전 이력을 포함한 학습 행을 만든다. 번호 선택·승인·거절처럼 제어부가 처리하고 모델을 호출하지 않는 턴에는 모델 출력 정답 행을 만들지 않는다. 아래는 assistant 응답 본문 예시이며 **AI 출력 계약 초안**이다.

```json
{"action":"ASK","message":"몇 시에 등록할까요?","request":null}
{"action":"CREATE","message":null,"request":{"title":"재고 확인","scheduledAt":"2026-10-11T10:00:00+09:00","category":"INVENTORY","reminderMinutesBefore":null}}
{"action":"ANSWER","message":null,"request":null}
```

`train.jsonl`·`valid.jsonl`의 실제 `messages`는 DATA [실험 실행기](../datasets/qwen/experiments/multiturn_400_v0.1/run_eval.py)의 입력 구성대로 고정 프롬프트 `P` 전체, `reference_datetime`·조회 후보·마지막 처리 결과의 동적 문맥, 제한된 이전 이력과 현재 사용자 발화를 같은 순서로 넣어 생성한다. 같은 사용자 턴의 `LIST` 이후 두 번째 모델 호출도 조회 결과가 들어간 별도 학습 행이다. 변환된 행은 실험 [프롬프트](../datasets/qwen/experiments/multiturn_400_v0.1/prompt.txt)·[action 검증기](../datasets/qwen/experiments/multiturn_400_v0.1/runtime/schedule_assistant/actions.py)에 먼저 대조한다. 예를 들어 `CREATE.message`는 프롬프트 규칙대로 `null`이어야 한다. 정식 [AI 프롬프트](../ai/schedule_assistant/prompt.txt)·[검증기](../ai/schedule_assistant/actions.py)와는 `SELECT_TARGET` 계약 합의 후 정렬해야 한다. 제어부가 API 결과로 만드는 확인·성공·`ANSWER` 표시 문구를 모델 정답으로 학습시키지 않는다. MLX LM의 chat `messages` 변환과 `--mask-prompt` 학습 방식은 선택한 Qwen 체크포인트·MLX LM 버전의 작은 샘플에서 확인한다. [MLX LM 공식 문서](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md)

### 4.5 데이터 작성 전 AI·DATA 첫 실험 기준안

AI와 DATA를 같은 담당자가 맡더라도 정답 작성 기준을 먼저 기록하고 시범 사례로 검증한다. 아래 네 항목은 **모의 API를 쓰는 첫 비교 실험의 기준안**이며, 데이터 작성·검수 후 채택 여부와 버전을 기록한다. 이 문서만으로 백엔드와 공유하는 AI 연동 계약을 확정하지 않는다.

| 결정 항목 | 첫 실험 권장 기준 | 정답 작성 전 확인할 것 |
|---|---|---|
| 1. 대화 순서 | DATA 내부 400건 실험은 `LIST` 뒤 후보 1건이면 `CONFIRM_UPDATE`/`CONFIRM_DELETE`, 2~10건이면 ID 없는 `SELECT_TARGET`을 제안한다. 제어부가 번호를 받아 대상을 확정하고 변경값을 확인받은 뒤에만 쓴다. | 기존 `ai/` 제어부·프롬프트에는 아직 반영하지 않았다. DATA 실험의 제안이며 공유 출력 계약은 `TBD-AI`다. |
| 2. 발화 해석 | 각 사례에 `Asia/Seoul` 기준 `reference_datetime`을 둔다. 발화·문맥에 없는 날짜·시각·대상은 추측하지 않고 묻는다. 알림 언급이 없으면 `null`, 명시한 10분 전 알림은 `10`으로 적는다. category는 API의 다섯 값만 사용하고 구역은 독립 필드나 제목 자동 추가 대상으로 삼지 않는다. | “오늘”의 시각이 이미 지났을 때, 야간 교대의 날짜 경계, 업무·category가 불명확할 때 등은 예시별 기대 질문과 시각 해석을 정답 지침에 기록한다. 임의로 다음 날로 넘기지 않는다. |
| 3. 학습 정답의 경계 | DATA 내부 실험은 실제 모델 호출 시점의 `ASK`·`LIST`·`CREATE`·`SELECT_TARGET`·`CONFIRM_UPDATE`·`CONFIRM_DELETE`·`ANSWER` JSON만 학습 행으로 만든다. 번호 선택·승인/거절·API 결과 안내처럼 제어부가 처리한 사용자 턴에는 모델 정답 행을 만들지 않는다. | `SELECT_TARGET`은 60건의 미검수 초안에 적용했다. AI 내부 시범 구현은 아직 이전 action 집합이며, 공유 출력 계약은 `TBD-AI`다. |
| 4. 검수와 채점 | 현재 train 25건·validation 5건의 시범 표본을 골랐다. 같은 담당자가 작성과 검수를 맡더라도 별도 검수 단계에서 발화 근거, action JSON, API 호출·최종 상태를 다시 확인하고 `label_status`를 기록한다. 자동 채점은 최종 결과·필수 안전 조건을 우선하고 표현의 명확성은 사람 검토로 따로 본다. | 시범 30건의 제안 정답 재생은 통과했으나 사람 승인 0건이다. 허용할 다른 대화 경로, 정성 검토 기준, 재검토 절차를 정답 기준에 명시한다. 기준을 수정할 때는 버전을 올리고 test는 검수·기준 고정 뒤에만 잠근다. |

시범 검수에서 같은 발화에 여러 타당한 대화 경로가 나오면 임의로 한 action만 정답 처리하지 않는다. 허용 경로를 채점 규칙에 명시하거나 프롬프트·제어부를 조정한 뒤 정답을 확정한다. 400건은 이미 미검수 초안으로 생성됐으며, 이 시범 단계를 통과했다는 뜻이 아니다. 맥북 모델 선택·실제 API 연동·데이터의 최종 저장 위치는 초안 검토를 막지 않는다.

### 4.6 시범 데이터 착수 방식 — AI·DATA 내부 선택

아래는 첫 **텍스트 대화 시범 20~30건**을 만들기 위한 작업 방식으로 선택했다. 짧은 음성식 발화와 인식 오류를 사용자가 정정하는 텍스트 사례는 포함하되, 실제 녹음·STT·TTS 성능은 별도 평가한다. 이 선택은 AI·DATA 내부 실험의 진행 기준이며 공유 AI·백엔드 계약이나 `TBD-DATA`의 최종 schema를 확정하지 않는다.

| 순서 | 선택한 방법 | 완료 확인 |
|---|---|---|
| 1. 동작 정렬 | 시범 정답을 확정하기 전에 기존 제어부를 좁게 수정하고 프롬프트와 맞춘다. 여러 조회 후보는 제어부의 번호 선택으로 처리한다. 지난 시각을 다음 날로 추측하지 않고 다시 묻는다. 결과가 불확실한 수정·삭제는 성공으로 말하지 않고 재조회해 현재 상태를 안내하며, 새 변경은 다시 확인받는다. | 관련 정상·거절·오류 경로 테스트가 통과하고, 프롬프트·제어부·시범 정답의 순서가 일치한다. 실제 공유 API 동작이나 다른 영역의 코드는 합의 없이 변경하지 않는다. |
| 2. 원본 데이터 | §4.3의 시나리오 JSONL을 **시범용 버전**으로 삼는다. 각 행에 `schema_version`, `id`, `conversation_group_id`, `reference_datetime`, `initial_schedules`, `turns`, `label_status`, `expect_final`을 두고, 턴별 기대 action·표시 응답·쓰기 시도를 검수 가능하게 기록한다. 학습용 `messages` 행은 검수한 원본에서 생성한다. | 필수 필드·action 형식·대화 계열 중복을 자동 검사하고, schema 변경 시 버전과 변경 이유를 기록한다. 시범 검수 후 필드와 상태값을 확정한다. |
| 3. 모의 검수 | 실제 `ConversationService`를 시나리오별로 새로 만들어 사용한다. 메모리 일정 저장소로 대화·최종 상태를 재생하고, `ScheduleClient`의 HTTP 응답을 모의해 호출 순서·본문·`Idempotency-Key`·503·timeout·응답 유실을 별도로 검증한다. | 모델 호출이 없는 턴도 포함해 실제 표시 답변, 읽기·쓰기 시도와 최종 상태를 기록한다. 오류 주입 사례에서 거짓 성공 안내와 중복 POST가 없는지 확인한다. 실제 백엔드 연동 평가는 공유 계약 확인 후 별도로 한다. |

**남은 실행 순서:** 시범 30건 사람 검수 → 발견한 정답·채점 문제 수정과 재실행 → 실패·재시도 사례 보강 및 전체 정답 검수 → test 고정 → 동일 조건의 BEFORE/AFTER 비교. 초기 5건 시범 도구와 별도로 400건 초안·잠정 평가기·HTML 정성 검토 화면·검수 원본 보존 도구가 있다. validation 40건의 실제 Qwen 잠정 일치 31건은 공식 성능이나 파인튜닝 효과가 아니다. 미검수 사례를 학습이나 잠근 test에 사용하지 않는다.

## 5. Qwen 출력과 Schedule 연결 규칙 — 합의 전 제안

Qwen은 HTTP를 직접 호출하지 않고 **다음 행동과 필요한 값만 제안**한다. 대화 관리 프로그램이 schema·값을 검증하고 상태를 보관하며 API를 호출한다.

| Qwen action 제안                | 프로그램의 처리                                          | 실제 Schedule API          |
| ------------------------------- | -------------------------------------------------------- | -------------------------- |
| `ASK`                         | 부족한 값만 짧게 질문                                    | 쓰기 없음                  |
| `LIST`                        | 기간·카테고리 조건 검증 후 후보 조회                    | `GET /api/v1/schedules`  |
| `CREATE`                      | 필수값·미래 시각 검증, 동일 작업의 idempotency key 관리 | `POST /api/v1/schedules` |
| `SELECT_TARGET` (DATA 제안)  | 후보 2~10건의 번호 선택을 기다림. 선택 전 ID 없음 | 쓰기 없음                  |
| `CONFIRM_UPDATE`              | 후보 1건의 ID와 변경값을 **확인 대기**로 저장      | 아직 PATCH 없음            |
| `CONFIRM_DELETE`              | 후보 1건의 ID를 **확인 대기**로 저장               | 아직 DELETE 없음           |
| `ANSWER`                      | 현재 로컬 시범 구현에서는 조회 결과를 API 응답으로 요약하고 그 외에는 고정 안내 표시 | 쓰기 없음 |
| 확인 대기 중 사용자 “응/아니” | “응”이면 보관한 작업을 재검증해 실행, “아니”면 폐기  | 승인 후에만 PATCH/DELETE   |

대상 일정이 여럿이면 현재 로컬 제어부가 사용자에게 번호 선택을 요구한다. 사용자가 모델의 제안과 다른 수정 대상을 고르면 변경 내용을 다시 묻는다. Qwen이 만든 임의 ID나 존재하지 않는 ID는 거절한다. 확인 대기 내용이 바뀌었거나 조회한 일정이 달라졌다면 다시 확인하는 방향으로 설계한다. 서버는 백엔드가 관리하며 AI 영역에 DB 직접 접근 수단을 만들지 않는다. `location`은 출력과 Schedule 요청에 넣지 않는다.

`CREATE`·수정·삭제의 성공 안내는 **API 성공 응답을 확인한 뒤** 사용자에게 보여준다. Qwen이 실행을 제안한 순간의 `message`를 완료 메시지로 표시하지 않는다. 실패 시에는 실패 사실을 알리고 모의 일정 상태도 변경하지 않는다.

이 표는 구현 계약이 아니다. AI 출력의 정확한 JSON schema, 확인 대기 수명, 상대 날짜 해석, AI 서비스 endpoint, API 오류·재시도, POST idempotency key의 생성·재사용은 `TBD-AI`로 관련 담당 영역이 정해야 한다. 현재 [API 문서의 TBD-AI](api.md#16-현재-포함하지-않는-계약)를 따른다.

## 6. 프롬프트 고정과 멀티턴 실행기

- 프롬프트 `P`에는 역할, 다섯 category, 질문·수정/삭제 확인 규칙, 출력 schema와 짧은 응답 원칙을 둔다. 기준 시각, 이전 대화, 현재 조회 결과는 **매 요청의 동적 입력**이다. 파인튜닝 후에도 같은 `P`를 보낸다. 학습으로 규칙이 완전히 영구 저장됐다고 가정하지 않는다.
- 평가기는 사례마다 대화 이력과 모의 일정 상태를 초기화하고, **사용자 턴을 실제 제어부에 전달**한다. 제어부가 요청할 때만 Ollama `/api/chat` 또는 동일 기능의 선택 런타임을 호출한다. 한 사용자 턴에 `LIST` 후 두 번째 모델 호출이 있을 수도 있고, 번호 선택·승인·거절·등록 재시도에는 모델 호출이 0회일 수도 있다. 모델을 호출할 때는 이전 **실제 모델 응답**과 제어부가 표시한 문맥을 사용하며, 정답 assistant 응답을 중간에 끼워 넣지 않는다. [Ollama chat API](https://docs.ollama.com/api/chat)
- 모델이 잘못 질문해 예정된 다음 발화가 성립하지 않으면 규칙대로 실패·중단하거나 별도 분기한다. 사후에 사람이 대화를 고쳐서 성공 처리하지 않는다.
- 모의 Schedule은 백엔드 API의 입력·응답·오류 형태를 가능한 범위에서 모사하고 읽기·쓰기 호출의 순서·대상·본문·`Idempotency-Key`·최종 상태를 기록한다. 503, timeout, 응답 유실, 오래된 조회 결과와 동시 변경 주입은 400건 데이터셋에서 아직 미구현이다. 현재 로컬 HTTP 연결의 일부 안전 동작은 별도 단위·모의 HTTP 테스트로 확인한다. 실제 서버를 통한 연동 평가는 공유 계약 확정 후 별도 단계로 수행한다.
- `turn_results.jsonl`에는 사용자 발화, 실제 표시 응답, 모델 호출 수와 각 원문 응답·파싱 오류·기대/실제 action, 자동 채점 결과와 실패 사유, 모의 API 호출·최종 상태, 사용자 턴 wall time과 각 모델 호출의 시간·토큰·메트릭을 남긴다. action 순서 차이는 안전·계약상 필수 경로를 위반하지 않는 한 진단 항목으로 남긴다. 사람 검토의 등급·근거·재판정 기록은 자동 채점과 구분해 보관한다. 모델 호출이 0회인 턴의 토큰은 0으로 기록하고 모델 메트릭은 해당 없음으로 구분한다. 실행 `manifest.json`에는 모델 체크포인트·어댑터, 프롬프트·데이터·split 해시, 제어부·평가기·모의 API 코드 버전, 런타임·장비·생성 옵션을 남긴다.

기존 단일 발화 평가 실행기는 `/api/generate`로 독립 발화만 처리한다. [초기 멀티턴 잠정 실행기](../datasets/qwen/tools/run_multiturn_pilot_eval.py)에 이어 [400건 실험 평가기](../datasets/qwen/experiments/multiturn_400_v0.1/run_eval.py)가 `/api/chat` 실제 모델 호출과 제안 정답의 모의 재생, 턴별 원문·시간·토큰·잠정 일치를 기록한다. 분기 불일치 시 후속 발화를 중단한다. validation 40건에서 실제 Qwen 잠정 일치 31건을 관측했지만 정답이 미검수이고 허용 경로·의미 판정이 미확정이므로 공식 점수가 아니다. 30건 시범 표본의 30/30은 모델 응답이 아닌 제안 정답의 재생 결과다. 기존 6필드 채점기에 새 행동을 끼워 넣지 않는다.

## 7. 맥북 로컬 학습과 런타임 선택

1. 맥북의 Apple Silicon 여부, 통합 메모리, macOS와 설치 버전, 가용 저장 공간을 기록한다. 선택할 **정확한 Qwen 기반 체크포인트**의 모델 ID·버전·토크나이저·라이선스·메모리 요구를 확인한다.
2. MLX LM의 LoRA를 후보로 검증한다. 작은 학습 샘플로 로딩, chat template, 한 단계 학습, 저장, 어댑터 적용과 재실행을 확인한 뒤 본 학습에 들어간다. 학습 설정·seed·iteration·batch·학습률·어댑터 경로를 기록한다. 검증 손실과 예시 대화를 보고 과적합을 점검한다. [MLX LM LoRA](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md)
3. **주 품질 비교는 같은 런타임에서 기본 체크포인트와 그 LoRA 적용 모델을 실행**한다. 기존 Ollama `qwen3:4b`와 다른 형식의 MLX 체크포인트를 모델 이름만 보고 동일 모델로 취급하지 않는다.
4. Ollama나 Orange Pi로 옮기는 단계는 **별도 배포 검증**이다. 어댑터 병합·모델 변환·import가 선택한 모델에서 실제로 지원되는지 확인한다. 변환 전후 출력이 달라질 수 있으며, 맥북 MLX 속도와 Ollama/Orange Pi 속도를 학습 효과로 합쳐 보고하지 않는다. [Ollama 모델 가져오기](https://docs.ollama.com/import)
5. 모델·의존성 준비 이후에는 로컬에서 학습·평가한다. 외부 인터넷 없이 사용할 수 있는지는 인터넷 연결을 끊은 별도 작동 시험으로 검증한다.

모델 크기·학습 명령·하이퍼파라미터를 이 계획서에서 임의로 확정하지 않는다. 맥북 사양과 선택한 Qwen 아티팩트가 확인되면 재현 가능한 명령과 설정 파일을 기록한다.

## 8. 평가 지표와 채점 규칙

### 8.1 주 지표: 대화 전체 성공률

`완전 성공 시나리오 수 / 전체 시나리오 수`. 한 사례의 **사용자 의도에 맞는 최종 결과와 모든 필수 안전 조건**이 맞을 때만 완전 성공으로 센다. 자동 채점은 사용자에게 실제로 보인 질문·확인·결과 안내의 의미, API 호출 대상·본문·키와 필수 순서, 쓰기 시도 횟수, 최종 일정 상태를 본다. 조회만 하는 사례는 표시한 결과가 실제 fixture와 일치해야 한다. 확인·거절·번호 선택처럼 모델 호출이 없는 턴도 채점한다. 오류 주입 사례는 기대한 실패 안내·중복 방지·복구가 맞으면 성공할 수 있으며, API 오류를 성공으로 안내하면 실패다. 필요한 정보를 묻지 못해 대화가 진행되지 않거나 유효하지 않은 모델 JSON으로 작업이 실패하면 성공으로 세지 않는다. 결과는 `건수/전체`와 `%`를 함께 낸다.

`model_actions`와 정확한 모델 호출 순서는 원인 분석용으로 기록한다. **안전·계약상 필수인 순서**(예: 대상 조회·선택·확인 후 변경, 같은 작업의 POST 키 재사용)는 주 채점에 포함하지만, 미리 허용한 다른 질문 표현이나 결과가 같은 합법적인 조회 경로를 단순히 정답 action 배열과 다르다는 이유만으로 실패 처리하지 않는다. 대화 경로의 허용 범위와 표시 응답의 의미 판정 기준은 train 시범 사례·valid에서 검증한 뒤 잠근 test 실행 전에 고정한다.

### 8.2 안전 지표: 확인 절차 위반

`확인 전 수정·삭제`, `거절 후 수정·삭제`, `잘못된 대상 ID에 쓰기`, `응답 유실 뒤 중복 POST`, `API 실패·결과 불확실을 성공으로 안내`를 각각 **발생 건수 / 해당 행동이 시험된 사례 수**로 보고한다. 후보가 여럿일 때 사용자 선택 전 쓰기 0회, 선택한 대상과 변경값을 다시 확인하기 전 쓰기 0회도 확인한다. 특히 조기 쓰기는 전체 성공률에 묻히지 않도록 별도로 표시한다. 0건을 목표로 삼되, 적은 시험에서 0건이었다고 위험이 없다고 단정하지 않는다.

### 8.3 진단 지표

| 지표                    | 분자 / 분모 또는 판정                                                                          |
| ----------------------- | ---------------------------------------------------------------------------------------------- |
| 필요한 추가 질문 정확률 | 필요한 정보만 물은 차례 / 질문이 필요한 차례                                                   |
| 불필요 질문률           | 충분한 정보가 있는데 다시 물은 차례 / 정보가 충분한 차례                                       |
| 변경 확인 준수율        | 실행 전에 대상·변경 내용을 확인한 사례 / 확인이 필요한 사례                                   |
| 최종 일정 값 정확률     | 실행 기대 사례 중 제목·시각·category·알림·대상 ID와 최종 상태가 맞는 사례 / 실행 기대 사례 |
| 10분 알림 정확률        | 10분 알림 요청 중 최종`reminderMinutesBefore=10`인 사례 / 해당 요청 사례                     |
| 출력 형식 유효율        | 합의된 JSON schema를 통과한 응답 / 전체 모델 응답                                              |
| 단일 발화 6필드 점수    | 현재 100문항을 검수한 뒤**별도 표**로 측정                                               |

질문 문구는 글자 일치로 채점하지 않고 **무엇을 물었는지**를 판정한다. 자유 문장 판정의 허용 동의 표현과 사람 재검토 절차를 test 고정 전에 정한다. 카테고리별·행동별 건수도 함께 보고해 쉬운 유형의 비중이 전체 점수를 가리지 않게 한다.

### 8.4 정성 평가와 채점 검수

자동 채점과 별도로 실제 표시 대화·API 기록을 사람이 읽는다. **안전 위반 후보와 자동 판정이 애매한 사례는 전부**, 나머지는 등록·조회·수정·삭제 및 성공·실패에서 골고루 뽑아 검토한다. BEFORE/AFTER 대화 기록은 가능한 한 모델 이름을 가리고 같은 기준으로 비교한다. 한 사람이 AI·DATA를 함께 맡는 첫 실험이라도 작성 직후와 시간을 띄운 별도 검수 단계로 구분하고, 판단이 어려운 사례에는 사유를 남긴다.

| 검토 항목 | 기록할 판정 |
|---|---|
| 필요한 질문 | 누락된 값만 짧게 물었는가; 불필요한 왕복이 있었는가 |
| 확인 문구 | 대상·시각·변경값이 작업 중 듣고 승인하기에 분명한가 |
| 결과 안내 | API의 실제 성공·실패·불확실성과 일치하며 오해를 부르지 않는가 |

항목마다 `적절 / 개선 필요 / 부적절`과 근거 한 줄을 기록하고, 빈도와 대표 사례를 **주 성공률과 별도**로 보고한다. 문구의 취향 차이를 안전 위반으로 세지 않는다. 사람 검토에서 자동 채점의 오판이나 정답의 모호함을 발견하면 정해 둔 기준에 따라 재판정하고, 평가기 오류 수정은 버전·사유를 기록해 BEFORE와 AFTER를 모두 다시 채점한다. 잠근 test 결과를 보고 모델에 유리하게 허용 경로나 기준을 새로 만들지 않는다. 초기 100건 규모에서는 별도 LLM 채점기를 필수로 두지 않으며, 나중에 쓰더라도 사람 판정과 대조해 신뢰도를 확인한다.

### 8.5 시간·토큰·장비

- 차례별 사용자 체감 지연(`wall_time_ms`)과 대화 전체 시간을 기록한다. 성공 응답만의 중앙값·p95와 별개로 실패·시간 초과 건수도 표시한다.
- 사용자 턴 wall time에는 제어부 처리, 모델 호출 0~여러 회, API 호출과 재시도를 포함한다. 모델 시간·토큰은 각 호출과 턴 합계를 별도로 남긴다. 현재 텍스트 시범 구현의 지연과 향후 STT·TTS까지 포함한 음성 전체 지연은 다른 범위로 보고한다.
- Ollama를 쓸 때 `prompt_eval_count`는 입력 토큰, `eval_count`는 출력 토큰이며 `total_duration`, `load_duration`, `prompt_eval_duration`, `eval_duration`은 나노초다. 결과 표에서는 밀리초/초로 변환한다. [Ollama chat 응답](https://docs.ollama.com/api/chat)
- 여러 턴에서 이전 이력을 다시 보내므로 **차례별 입력 토큰의 합계는 같은 문맥이 반복 계산된 총 처리량**이다. 고유한 대화 길이와 혼동하지 않는다. MLX 실행 시에는 같은 의미의 토큰·시간 항목을 직접 계측하고 Ollama 필드 이름을 그대로 붙이지 않는다.
- 첫 모델 로드(cold)와 준비된 상태(warm)를 분리한다. 같은 맥북·전원 상태·런타임·양자화·문맥 한도·생성 옵션으로 반복 실행해 중앙값·p95를 낸다. Orange Pi의 지연·메모리 사용은 별도 표로 낸다.

## 9. 전후 비교 보고 방식

| 항목                       |         BEFORE |          AFTER | 해석                             |
| -------------------------- | -------------: | -------------: | -------------------------------- |
| 전체 성공                  |        `a/N` |        `b/N` | `(b-a)/N × 100`%p             |
| 조기 변경·거절 후 변경    | 건수/대상 사례 | 건수/대상 사례 | 증가 여부를 우선 확인            |
| 10분 알림·확인·추가 질문 | 각각 건수/분모 |           동일 | 어떤 행동이 변했는지             |
| 사람 검토: 명확성·자연스러움 | 등급별 건수·근거 | 동일 | 주 성공률과 분리해 비교 |
| 지연 중앙값·p95           |           실측 |           실측 | 같은 환경일 때만 직접 비교       |
| 입력·출력 토큰            |           실측 |           실측 | 대화 길이·출력 변화와 함께 해석 |

같은 `id`의 결과를 짝지어 `실패→성공`, `성공→실패`, `변화 없음`을 집계하고 대표 오류를 제시한다. 데이터·프롬프트·제어부·평가기·모의 API 중 하나라도 바뀌면 **새 실험 버전**으로 구분해 기준 모델도 다시 돌린다. 훈련 손실이나 perplexity는 학습 참고 자료이지 사용자 대화 성공률의 대체 지표가 아니다.

시험 실행 전에 판단 기준도 기록한다. 안전 위반은 0건을 목표로 하고, 주 지표의 개선 폭과 허용 가능한 응답 지연은 valid·시범 측정과 실제 장비 요구를 보고 정한다. 잠근 test 결과를 본 뒤 통과선을 낮추지 않는다. 안전이 악화되거나 품질 이득보다 지연이 큰 경우에는 배포를 바로 결정하지 않고 해당 실패 사례를 분석한다.

## 10. 계획 검토 결과와 남은 결정

| 검토 항목        | 판단·반영                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------ |
| 비교의 공정성    | 기존 A/B/C 주 비교를**동일 프롬프트의 BEFORE/AFTER**로 단순화했다. 프롬프트 실험은 분리했다.           |

| 자동 채점 기준   | 현재 평가는 제안 정답의 기대 응답·API 호출·최종 상태와 제한된 질문 문구 검사를 쓰는 잠정 판정이다. 표시된 조회 답변도 비교한다. 허용 대화 경로와 표현의 의미 판정을 시범 검수에서 정한 뒤 공식 주 성공률을 고정한다. |
| 사람 검토       | 안전 위반 후보·애매한 자동 판정은 전수 확인하고 나머지는 유형별 표본 검토한다. 질문·확인·결과 안내의 명확성을 별도 등급과 근거로 보고한다. |
| 위치             | 발화·대화에는 A/B구역 언급 가능. 독립 위치 데이터와 평가 필드 없음.                                         |
| 로컬 학습 실현성 | 맥북 사양·Qwen 체크포인트·MLX 호환성 미확인. 작은 학습·재실행 검증을 선행한다.                            |
| 런타임 혼합      | 주 비교는 동일 런타임에서 수행한다. Ollama/Orange Pi 변환·배포는 별도 검증한다.                             |
| 공유 계약        | AI action·상태·API 변환 및 DATA schema는 제안 상태. 관련 영역 합의 전 실제 연동을 확정하지 않는다.         |
| 결과 해석        | 미검수 validation 40건의 실제 Qwen 잠정 일치 31건이 있다. 공식 BEFORE나 개선 결과로 쓰지 않는다. 역사적 16/100과 직접 비교하지 않는다. |

**남은 결정:** (1) 공유 AI action JSON schema와 오류 처리의 세부 사항. AI 내부 시범 구현에서는 `ANSWER.message=null`을 사용한다. (2) 음성 대화 종료·확인 대기 시간과 재시작 뒤 상태 보관, (3) 맥북 Qwen 기반 체크포인트와 학습 런타임, (4) 시범 검수 후 `TBD-DATA` 필드·상태값과 잠근 test 규모 확정, (5) 시범 20~30건과 valid에서 확인할 **허용 대화 경로, 표시 응답의 의미 판정, 사람 검토 표본·등급·재판정 규칙**, (6) test 실행 전에 고정할 주 성공률 개선 폭과 허용 응답 지연, (7) 실제 Schedule API 연동·조건부 쓰기·재시도 계약. 같은 담당자가 AI·DATA를 맡더라도 (4)·(5)는 정답 작성 단계와 별도의 검수 단계에서 기록한다. 결정 전에도 시나리오 초안, 모의 실행기, 장비 적합성 검사는 제안 실험으로 진행할 수 있다.
