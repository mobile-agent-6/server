# 후보 C 학습 데이터 작성 기준

- Issue: #32
- 작성일: 2026-10-29 (Asia/Seoul)
- 대상: 후보 C 형식으로 수정, 삭제, 조회 데이터를 만드는 팀원
- 성격: Issue #32 학습 6회에서 확인한 기준을 모은 제안이며, 팀 확정 전이다.

## 1. 핵심 규칙 7가지

1. 모델 정답에는 **사용자 원문을 글자 그대로 복사한 근거**만 넣는다. 날짜 계산, 일정 ID, 결과 문구는 넣지 않는다.
2. 근거는 작업별로 정해진 **역할 칸**에 넣는다(3.1 표).
3. 한 기능만 넣지 말고 **다른 기능 사례도 섞는다.** 등록만 학습한 모델은 수정 요청을 등록으로 착각했다(run 004).
4. **멀티턴 정정**을 꼭 넣는다. "모레요" 뒤에 "모레 말고 글피로"처럼 앞 턴 값을 바꾸는 대화를 놓쳐 run 006이 멈췄다.
5. **시험 문제(locked56, Test 50)의 문장, 제목, 문장 형태를 따라 하지 않는다.**
6. 정답 JSON을 손으로 정렬하지 않는다. 학습 도구(`prepare_trial.py`)가 정해진 순서로 바꾼다. 알파벳 순서로 정렬했다가 학습 3회가 실패했다.
7. 만든 뒤에는 **작성자가 아닌 검수자가 한 번 더 전수 검수**한다.

## 2. 데이터 한 건의 구성

| 파일 | 내용 |
|---|---|
| `conversations-v0.1.jsonl` | 기준 시각, 초기 일정, 사용자 턴, 기대 결과 |
| `candidate-c-targets-v0.1.jsonl` | 모델 호출 턴마다의 정답 C 출력 |
| `review-events-v0.1.jsonl` | 검수 판정 기록 |

새 묶음은 `batch4/build_batch4.py`, `batch5/build_batch5.py`를 본떠 생성기로 만든다. 생성기에 검사를 넣어 두면 수정할 때마다 다시 확인할 수 있다.

## 3. 정답 모양

### 3.1 작업별 역할

| 작업 | targetEvidence (찾을 기존 일정) | changeEvidence (새 값) | filterEvidence (조회 조건) |
|---|---|---|---|
| create | 비움 | 제목, 날짜, 시간, 분류 | 비움 |
| update | 제목, 날짜, 시간, 분류, 완료 상태 | 바꿀 제목, 날짜, 시간, 분류, 완료 | 비움 |
| delete | 제목, 날짜, 시간, 분류, 완료 상태 | 비움 | 비움 |
| list | 비움 | 비움 | 제목, 날짜, 시간, 분류, 완료, 앞으로 남은 |

수정과 삭제의 대상 시간과 분류는 기존 일정을 좁히는 조건으로만 사용한다. 오전 또는 오후가 없는 대상 시간은 backend가 두 가능성을 모두 후보로 남기며 임의로 하나를 고르지 않는다. 조회 시간은 오전 또는 오후가 명확할 때만 사용하고, 모호하면 다시 질문한다.

### 3.2 근거 단어 규칙

- 근거마다 `turn`(몇 번째 턴), `text`(원문 그대로), `status`를 적는다.
- `status`: 채택한 값은 `adopted`, 버린 값은 `superseded`, "말고", "아니", "대신" 같은 정정 표지는 `correction_marker`.
- 제목에 요청 표현을 붙이지 않는다. "회의 취소해 줘"의 제목은 "회의"다.
- 공백, 조사, 숫자를 바꾸지 않는다. 원문에서 글자 단위로 복사한다.

### 3.3 지금까지 정한 관례

| 상황 | 근거 단어 |
|---|---|
| 분류 조건 "분류가 입고인 일정" | "분류가 입고인" (인 포함) |
| 분류 조건 "분류가 입고이고 …" | "분류가 입고" (이고 제외) |
| 완료 조건 조회 | "아직 안 끝난", "완료된", "미완료" |
| 앞으로 남은 일정 조회 | "앞으로 남은" |
| 완료 표시 수정 | 요청 표현까지 포함 ("완료로 표시해 줘") |
| 바꿀 값이 없는 수정 ("회의 바꿔 줘") | `missingInformation`에 `change_value` |

`완료 안 된`, `완료가 안 된`, `완료 처리 안 된`, `완료 전`뿐만 아니라 `완료 안됨`,
`완료 안 됨`, `완료 안됐어`, `완료 아님`, `완료가 아닌`, `완료 아니야`,
`완료 안 돼 있어`, `완료 처리 안 됨`도 미완료 조건으로 쓸 수 있다. `completed` 근거에는
부정을 포함한 연속 substring 전체를 넣는다. 긍정과 부정이 함께 있거나 의미가 모호한
문장은 임의로 하나를 고르지 말고 별도 검수한다.

## 4. 유형 구성

만들기 전에 **유형별 비중표**를 먼저 쓰고, 빠진 유형이 없는지 확인한다. run 001은 한 유형이 통째로 빠져 실패했다.

기능마다 넣을 상황:

- 정보가 모두 있는 요청
- 빠진 정보 → 되묻기 → 답변 (멀티턴)
- 같은 턴 정정 ("3시, 아니 4시로")
- **다음 턴 정정** ("모레요" → "모레 말고 글피로")
- 애매한 제목 ("그거 하나", "이거", "저번에 말한 그 건")
- 지원하지 않는 요청이 섞인 경우 ("옮기고 알림도 켜 줘")
- 동의 답변의 다양한 말투 ("해 주세요", "부탁해요", "필요 없어요")

다른 기능과 헷갈리기 쉬운 문장을 일부러 넣는다. 예: "옮겨 줘"(수정)와 "잡아 줘"(등록), "취소해 줘"(삭제)와 동의 거절.

여러 부탁을 한 번에 하는 대화는 각 기능 데이터가 모인 뒤 따로 만든다.

## 5. 시험 문제와 겹치지 않기

- locked56(`datasets/qwen/experiments/structured_output_contract_v0.1/locked-cases-v0.1.jsonl`)와 Test 50(`datasets/qwen/experiments/candidate_c_create_400_v0.1/test50/`)의 문장과 일정 제목을 쓰지 않는다.
- 생성기에서 문장 유사도(0.35 미만)와 제목 겹침을 자동 검사한다. `batch5/build_batch5.py`의 검사를 그대로 가져다 쓴다.
- 시험 문장에 제목만 바꾼 형태도 피한다. batch 5에서 이렇게 만든 사례가 있어 점수가 부풀 수 있다는 지적을 받았다.

## 6. 검사와 검수

- 자동 검사: `contracts.validate_candidate_c`(형식과 원문 일치), 신규 데이터는 `candidate_c_role_gate_v0_5`의 역할 검사.
- 기존 `common_gate_v0_2`부터 `common_gate_v0_4`와 해당 manifest, contract bundle은 과거 평가 재현용이므로 수정하지 않는다.
- 날짜, 시간 같은 정답 값은 사람이 직접 계산해 적는다. 생성기와 같은 함수로만 확인하면 같은 실수를 놓친다.
- 검수는 작성자가 아닌 검수자가 전수로 하고, 1차 판정 후 수정한 뒤 2차로 확인한다. 판정은 `review-events-v0.1.jsonl`에 남긴다.

## 7. 넘기는 방법

- 묶음 폴더(`batchN/`)를 만들어 작업 브랜치에 올린다.
- 학습 담당이 `prepare_trial.py`의 묶음 목록에 추가하고, **지금까지의 데이터 전체와 합쳐서** 학습한다. 기능별로 따로 학습하지 않는다.
- 학습 후 시험에서 틀린 유형을 알려 주면, 그 유형을 보강한 묶음을 추가한다.
