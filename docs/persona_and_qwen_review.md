# 프로젝트 페르소나와 Qwen 일정 대화 검토

> 작성일: 2026-10-10
> 페르소나 출처: 작업 사용자가 제공한 프로젝트 페르소나
> 검토 상태: DATA 영역의 평가 제안. AI 구조화 출력·호출·확인 절차는 `TBD-AI`이며 이 문서만으로 공유 계약을 확정하지 않는다.

## 1. 프로젝트 페르소나: 이정민, 31세

### 직업과 작업 환경

생활용품과 잡화를 취급하는 온라인 쇼핑몰 풀필먼트센터의 재고관리 및 피킹 담당 현장 작업자다. 주간과 야간 교대근무를 하며 A구역과 B구역을 이동하면서 재고 실사, 주문 상품 피킹, 재고 부족 수량 확인 업무를 수행한다. 필요에 따라 반품 상품 확인, 교대 인수인계, 팀 회의에도 참여한다.

### 업무 패턴과 어려움

정해진 작업 도중 특정 구역의 재고 재확인이나 반품 확인 같은 추가 업무를 전달받는다. 박스를 들거나 장갑을 착용하면 휴대폰을 직접 조작하기 어렵고, 추가 업무를 즉시 기록하지 못하면 다른 작업 중 놓칠 수 있다.

### 일정 비서 사용 목적

현장에서 전달받은 추가 업무를 음성으로 빠르게 등록하고 예정된 작업을 확인한다. 일정 비서, 일정 목록, 캘린더로 일정을 조회하며 필요한 작업에는 10분 전 알림을 설정한다.

대표 발화:

- “내일 오전 10시에 B구역 재고 확인하라고 알려줘.”
- “오늘 해야 할 반품 확인 일정 알려줘.”
- “재고 실사 시간을 오후 3시로 바꿔줘.”

### 기술 친숙도와 소통 선호

스마트폰의 기본 기능은 사용할 수 있지만 작업 중 복잡한 메뉴 탐색이나 여러 번 입력하는 방식은 부담스럽다. 짧고 명확한 답변과 간단한 조작을 선호한다. 작업 중에는 음성을 사용하고, 소음이 심하거나 말하기 어려우면 텍스트로 입력한다. 정보가 부족하면 간단한 추가 질문을 받고, 일정 변경 전에는 내용을 확인한다.

### 사용 결정 요인

음성 인식 정확도, 빠른 응답, 적은 조작, 정확한 일정과 알림, 외부 인터넷 없이 사용할 수 있는지를 중요하게 여긴다.

## 2. 페르소나 기준 대화 흐름 검토

다음은 사용자 요구를 바탕으로 평가해야 할 흐름이다. 현재 구현된 공유 AI 계약으로 해석하지 않는다.

1. 음성 또는 텍스트로 짧은 요청을 받는다. 소음 때문에 음성 입력이 어려우면 텍스트 입력으로 이어갈 수 있어야 한다.
2. 등록·조회·수정·삭제 의도와 일정의 날짜·시각·업무·구역을 파악한다. 피킹은 API의 `OUTBOUND`, 재고 실사는 `INVENTORY`, 반품 확인은 `RETURN`, 교대 인수인계·팀 회의는 `OTHER`에 해당한다.
3. 등록에 필요한 시각이나 수정 대상이 불분명하면 한 번에 이해하기 쉬운 짧은 질문을 한다. 문장에 없는 값을 임의로 채우지 않는다.
4. 일정 변경 전에는 대상 일정과 변경할 내용을 짧게 확인받는다. 대상이 모호한 삭제도 추가 확인이 필요하다.
5. 확인된 요청을 일정 기능에 반영하고 결과를 간결하게 안내한다. 사용자가 요청한 10분 전 알림은 일정 값과 함께 정확히 처리되어야 한다.

현재 Schedule API의 `category`는 `INBOUND`, `INVENTORY`, `OUTBOUND`, `RETURN`, `OTHER`이며, 일정 생성에는 `title`, `scheduledAt`, `category`가 필요하다. 10분 전 알림은 `reminderMinutesBefore`로 표현할 수 있다. 현재 Qwen 평가의 `location`은 API의 독립 필드가 아니다. AI 출력에서 API 요청으로의 변환과 대화 상태 관리는 `TBD-AI`다. [API 기준](api.md)

## 3. 현재 평가셋 점검

검토 대상은 [API 카테고리 기준 100문항](../datasets/qwen/experiments/api_categories/cases_100.jsonl)과 [현재 프롬프트](../datasets/qwen/experiments/api_categories/prompt.txt)다. 문항 정답은 `proposed_unreviewed`이며 새 모델 측정 결과는 없다.

| 항목 | 현재 상태 | 페르소나 관점의 판단 |
|---|---|---|
| 의도 | 등록·조회·수정·삭제 각 25건 | 기본 기능은 고르게 포함 |
| 카테고리 정답 | `INBOUND` 16, `INVENTORY` 17, `OUTBOUND` 34, `RETURN` 15, `OTHER` 4, `null` 14 | API enum은 일치하지만 기타와 재고 부족 상황이 적음 |
| 작업 구역 | 발화에 A구역 34건, B구역 35건, C구역 0건 | 제공된 A·B구역 작업 환경에 맞게 정리 |
| 알림 | 10분 전 알림·알림 설정 0건 | 핵심 사용 목적이 평가되지 않음 |
| 업무 맥락 | 교대 인수인계 1건, 팀 회의 1건, 재고 부족 수량 확인 0건 | 교대근무·추가 업무의 대표 장면이 부족 |
| 대화 | 단일 발화와 단일 JSON 출력 | 추가 질문·변경 전 확인·응답 간결성을 평가할 수 없음 |
| 기존 검토 표기 | 조회 `content` 규칙 누락 19건, 수정 대상/변경값 미분리 25건, 모호한 삭제 5건 | 정답 검수와 출력 규칙 결정이 필요 |

발화에 A구역과 B구역이 함께 나올 수 있으므로 구역 건수의 합계는 문항 수가 아니다. `null` 카테고리 14건은 업무 종류가 명시되지 않은 조회·삭제 요청이다.

## 4. 프롬프트와 평가 방식의 한계

현재 프롬프트는 현장 작업자 맥락을 명시하고 API의 5개 영문 enum을 요구한다. 피킹→`OUTBOUND`, 교대 인수인계·팀 회의→`OTHER` 규칙도 포함한다. 이 범위의 정적 분류·추출을 시험하는 데 사용한다.

프롬프트와 채점기는 `intent`, `date`, `time`, `location`, `category`, `content` 여섯 필드만 다룬다. 알림 요청, 여러 턴의 추가 질문, 변경 전 확인, 수정 대상 식별과 변경값 분리, 음성 인식 오류·소음·텍스트 전환, 실제 API 작업 성공과 오프라인 동작을 평가하지 않는다. 이 기능들을 여섯 필드에 임의로 끼워 넣어 점수화하지 않는다. 상대 날짜 기준일도 문항에 고정되어 있다.

## 5. 후속 결정과 검증

1. DATA 담당: 100문항의 날짜·`content`·구역·카테고리 정답을 검수하고, 알림·재고 부족·교대근무 사례를 별도 평가 범위로 제안한다.
2. AI 담당: 추가 질문, 수정·삭제 대상 식별, 변경 전 확인, 알림 요청을 표현할 출력과 대화 상태 방식을 제안한다.
3. BE·AI 등 관련 담당: AI 출력과 Schedule API 요청의 변환, 확인 후 실행 시점, `location` 처리 방식을 합의한다.
4. 합의 후 새 평가셋과 채점 규칙을 버전으로 고정하고 같은 조건에서 Qwen을 재실행한다. 초기 v0.1 점수와 직접 성능 비교하지 않는다.
